Insertion sort, stability and sorting by keys

Bubble and selection sort swap things around. Insertion sort sorts the way you sort cards in your hand: it shifts bigger cards aside and drops the new one into the gap. Today you'll also see why "stable" matters, sort objects by two keys, and sort without comparing at all.

1. Sorting the cards in your hand

Your left hand holds cards that are already in order. You pick up the next card (call it key), slide every bigger card one place to the right, and put key into the gap that opens up.

for (let i = 1; i < arr.length; i++) {
  const key = arr[i];               // lift the card out: arr[i] is now a "hole"
  let j = i - 1;
  while (j >= 0 && arr[j] > key) {
    arr[j + 1] = arr[j];            // shift the bigger card right, into the hole
    j--;
  }
  arr[j + 1] = key;                 // drop the card into the hole
}

Invariant: at the start of every round, arr[0..i-1] is sorted. Round i makes arr[0..i] sorted, so after the last round everything is.

Shift, don't swap. A swap is three writes (temp, a, b). A shift is one write. The key is held in a variable the whole time and written only once, at the end.

3. Best case, worst case

The work is all in the while loop, and the while loop runs once per shift. Every shift fixes exactly one pair of values that were in the wrong order (an inversion), so shifts = inversions.

Input (n items)ShiftsTime
already sorted [1, 2, 3, 4]0O(n): one look per item
nearly sorted (a few items out of place)a fewclose to O(n)
randomabout n²/4O(n²)
reverse sorted [4, 3, 2, 1]1 + 2 + … + (n-1) = n(n-1)/2O(n²)

Extra space is O(1): only key, i and j. Compare with bubble sort on Day 6: both are O(n²), but on nearly sorted data insertion sort does almost nothing, which is why real sort libraries use it for small pieces.

4. Stable vs unstable

A sort is stable if items with equal keys stay in the order they came in. Below each card is a number (the key) and a letter (just a label, to tell twins apart). We sort by the number only.

input:     [2a, 1b, 2c, 1d]
stable:    [1b, 1d, 2a, 2c]   // b before d, a before c: like the input
unstable:  [1d, 1b, 2a, 2c]   // also sorted by number, but b and d swapped places

Insertion sort is stable because it shifts only while arr[j] > key: a card never jumps over an equal card. Watch 2c stop behind 2a:

One character breaks it. Write >= instead of > and equal cards jump over each other: still sorted, no longer stable (and it does extra shifts for nothing). Selection sort from Day 6 is unstable for another reason: its long-distance swap can carry an item past its twin.

When does it matter? When you sort objects by one field and the existing order means something: sort a list of sign-ups by city and, within each city, they should still be first-come first-served. JavaScript's arr.sort is guaranteed stable.

5. Comparators with several keys

You met comparators in JS for DSA Day 9: return a negative number if a goes first, positive if b goes first, 0 for a tie. With two keys, compare the first key, and look at the second key only on a tie:

const people = [
  { name: "Ravi", age: 30 }, { name: "Asha", age: 25 }, { name: "Dev", age: 30 },
];
const byAgeThenName = people.slice().sort((a, b) => {
  if (a.age !== b.age) return a.age - b.age;   // first key: age
  return a.name.localeCompare(b.name);          // tie: name A to Z
});
// Asha 25, Dev 30, Ravi 30

Strings can't be subtracted. "Dev" - "Ravi" is NaN, and a comparator that returns NaN gives a garbage order. Use a.localeCompare(b): negative, 0 or positive, just like a - b. And copy first with slice(): sort changes the array it is called on.

Descending on a key? Flip that one subtraction: b.age - a.age. Each key can go its own way.

6. Counting sort: sorting without comparing

Every sort so far compares two items at a time, and a comparison sort can never beat O(n log n). But if the values are small whole numbers, say 0 to 4, you don't need to compare: count how many of each value there are, then write them back out in order.

Two passes: n steps to count, then k + n steps to write out (k = number of possible values). That's O(n + k) time and O(k) extra space. It's great for exam marks 0 to 100 or ages; it's hopeless for values up to a billion (a count array of a billion slots).

7. Predict the output

Work it out on paper first, then reveal.

How many shifts does insertion sort make on [1, 2, 3, 4, 5]? On [5, 4, 3, 2, 1]?

0 and 10. Sorted input never enters the while loop. Reverse sorted: the 4 shifts 1, the 3 shifts 2, the 2 shifts 3, the 1 shifts 4: 1 + 2 + 3 + 4 = 10 = 5 × 4 / 2.

How many shifts on [2, 1, 4, 3]?

2. Count the pairs in the wrong order: (2, 1) and (4, 3). One shift each.

["bb", "a", "ab"].sort((x, y) => x.length - y.length)

["a", "bb", "ab"]. "bb" and "ab" tie on length, and sort is stable, so they keep their input order. If you wanted "ab" first, you needed a second key.

[3, 1, 2].sort((a, b) => a > b)

[3, 1, 2] in Node and Chrome: not sorted at all! The comparator returns true/false, which become 1 and 0, never a negative number, so it can never say "a goes first". Return a - b.

Counting sort of [1, 0, 1, 1] with maxValue 2: what is the count array?

[1, 3, 0]: one 0, three 1s, no 2s. Its length is maxValue + 1 = 3, so slot 2 exists even though no 2 appears.

where this shows up

Interviews: "sort colors" (0/1/2) is a classic; the counting answer is fine, and on Day 9 you'll do it in one pass. Two-key comparators come up all the time: sort intervals by start then end, sort by frequency then value, sort log lines by several fields. "Insert into a sorted list" is the inner step of many problems (and of keeping a running median).

Later topics: TimSort, the algorithm behind most real sort functions, runs insertion sort on small chunks and then merges them, which is exactly tomorrow's topic. Counting is the base of bucket sort and radix sort. Shifts = inversions, and tomorrow you'll count inversions much faster with merge sort.
