Quick sort and quickselect

Pick one value, the pivot, and put it exactly where it belongs: smaller values to its left, the rest to its right. Do that again on each side and the array is sorted. Do it on just one side and you find the k-th smallest value in about O(n).

← Day 8Day 10 →

1. Partition: one pass, one value placed for good

Partitioning around a pivot means: rearrange the array so every value less than the pivot comes before it and every other value comes after it. The two sides don't have to be sorted. But the pivot itself is now in its final sorted position: exactly as many values are smaller than it as there are boxes to its left.

before:  [6, 2, 9, 1, 7, 3, 8, 4]      pivot = 4 (the last value)
after:   [2, 1, 3, 4, 7, 9, 8, 6]
          < 4      ↑  >= 4 (any order)
                   4 is at index 3, where it will be in the sorted array

2. Watch it run: the Lomuto partition

The Lomuto scheme takes the last value as the pivot and keeps a "small zone" at the front: arr[lo..i-1] holds the values found so far that are < pivot. j scans; whenever it finds a small value, it swaps it to the end of the small zone and grows the zone. At the end, the pivot swaps in right after the small zone.

Green = small zone, orange = arr[j] being compared, blue = the pivot.

Strictly less. Every question today uses arr[j] < pivot, so values equal to the pivot end up on its right. With <= you'd still get a valid partition, just a different one, and the tests expect this exact one.

3. Quick sort: partition, then recurse on both sides

function sortRange(arr, lo, hi) {
  if (lo >= hi) return;                  // 0 or 1 values: already sorted
  const p = partitionRange(arr, lo, hi); // pivot lands at p, for good
  sortRange(arr, lo, p - 1);             // sort the values left of it
  sortRange(arr, p + 1, hi);             // sort the values right of it
}
sortRange(arr, 0, arr.length - 1);

4. The worst case: sorted input

A good pivot lands near the middle: two halves, log n levels, O(n log n), just like merge sort. But on an already sorted array, the last value is always the biggest. It lands at the end, the right side is empty, and the left side is only one value smaller. Watch the comparisons counter:

(n−1) + (n−2) + … + 1 = n(n−1)/2 comparisons: O(n²), and the recursion goes n calls deep. For 100,000 sorted values that's 5 billion comparisons, and a stack overflow.

The fix is a better pivot. Real implementations pick a random index as the pivot (swap it to the end, then do Lomuto as usual), or the median of the first, middle and last values. Then no particular input is reliably bad, and the expected time is O(n log n). Today we keep the last value so every answer is predictable.

5. Quickselect: only follow one side

Want the k-th smallest value? In the sorted array it would sit at index k - 1. After one partition, the pivot is at its sorted index p. Compare:

p === k - 1   → the pivot IS the answer
p <  k - 1    → the answer is on the right: lo = p + 1
p >  k - 1    → the answer is on the left:  hi = p - 1

Like binary search, but the "halves" come from partitions. Here we look for the 7th smallest (target index 6). Dimmed boxes have been thrown away:

On average the range halves each time: n + n/2 + n/4 + … ≈ 2n, so quickselect is O(n) on average. That beats sorting first (O(n log n)) when you only need one value.

6. Three-way partition: the Dutch national flag

If there are only three values (0, 1, 2), one pass with three pointers sorts it in place:

[ 0 0 0 | 1 1 1 | ? ? ? ? | 2 2 2 ]
          ↑       ↑       ↑
         low     mid     high
  • arr[mid] is 0: swap it with arr[low]; low++ and mid++.
  • arr[mid] is 1: it's already in the 1s zone; mid++.
  • arr[mid] is 2: swap it with arr[high]; high--. (Don't move mid: the value that came from high hasn't been looked at.)

Stop when mid > high: the unknown zone is empty. That's Q6. On Day 7 you counted then rewrote (two passes); this does it in one.

7. Predict the output

Work it out on paper first, then reveal.

Lomuto partition of [3, 7, 1, 5]: where does the pivot land?

Index 2, giving [3, 1, 5, 7]. Pivot 5: 3 is small (i = 1), 7 isn't, 1 is small (swap with 7, i = 2), then the pivot swaps with arr[2] = 7.

Lomuto partition of [9, 8, 7, 1]?

[1, 8, 7, 9], pivot index 0. Nothing is < 1, so the small zone stays empty and the pivot swaps with arr[0]. Notice 9 jumped from the front to the back: that kind of long jump is why quick sort is not stable.

How many comparisons does quick sort (last-value pivot) make on [1, 2, 3, 4, 5]?

10 = 4 + 3 + 2 + 1. Every pivot is the biggest in its range, so each partition only removes one value.

On [2, 2, 2, 2, 2], is quick sort fast?

No: also 10 comparisons, the worst case. Nothing is strictly less than the pivot, so the pivot always lands at the front and one side is empty. (A three-way partition would finish in one pass.)

Quickselect for the 1st smallest of [4, 3, 2, 1, 5]: how many partitions?

Pivot 5 lands at index 4 (too far right), then pivot 1 of [4, 3, 2, 1] lands at index 0, the target. 2 partitions.

where this shows up

Interviews: "k-th largest element in an array" (quickselect or a heap), "top k frequent elements", "sort colors" (Dutch flag), "move zeros", "segregate negatives and positives", "wiggle sort" all use partitioning. "Why is quick sort O(n²) on sorted input, and how do you fix it?" is a classic question.

Later topics: Phase 2 (array and string patterns) leans on partition-style two pointers. Heaps (Phase 3) give another way to do top-k in O(n log k). Randomized algorithms, like the random pivot, come back in hashing.
