Merge sort: divide and conquer

Bubble, selection and insertion sort all hit O(n²). Merge sort beats them with one idea: two sorted halves can be merged in a single pass. Split, sort each half recursively, merge. O(n log n), every time.

← Day 7Day 9 →

1. Divide and conquer

A big new way of thinking, built on the recursion from Days 3–5:

  1. Divide the problem into smaller problems of the same kind,
  2. conquer each one recursively (a tiny one is a base case), and
  3. combine their answers into the answer for the whole.

For sorting: split the array in half, sort the left half, sort the right half, then combine them. A one-item array is already sorted, which is the base case. All the real work happens in the combine step: merge.

2. Merging two sorted arrays

If a and b are both sorted, the smallest value left anywhere is at the front of a or at the front of b. So compare only the two fronts, take the smaller, and move that pointer on.

function merge(a, b) {
  const out = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) {
    if (a[i] <= b[j]) out.push(a[i++]);
    else out.push(b[j++]);
  }
  while (i < a.length) out.push(a[i++]);   // leftovers of a
  while (j < b.length) out.push(b[j++]);   // leftovers of b
  return out;
}

Below, the first four boxes are a and the last three are b. Taken values fade out. Each value is pushed once, so merging is O(n + m).

Don't forget the leftovers. The main loop stops as soon as ONE array is used up. Without the two little loops at the end, you silently lose the rest of the other array. And use <=, not <: on a tie take from a first, so equal values keep their order and merge sort is stable.

3. Merge sort

function mergeSort(arr) {
  if (arr.length <= 1) return arr.slice();      // base case: already sorted
  const mid = Math.floor(arr.length / 2);
  const left = mergeSort(arr.slice(0, mid));    // trust the recursion
  const right = mergeSort(arr.slice(mid));
  return merge(left, right);                    // combine
}

Read it with the recursion mindset from Day 3: don't follow every call in your head. Assume mergeSort correctly sorts a smaller array; then all this call has to do is merge two sorted halves, and you already know merge is right.

4. Watch it run: split, then merge

The same algorithm, passing indices instead of slicing (the trick from Day 4): mergeSort(arr, lo, hi) sorts arr[lo..hi-1]. The highlighted boxes are the piece the current call works on; the stack on the right shows which calls are waiting.

Notice the order: the left half is completely sorted before the right half is even split. That's the call stack at work, exactly like the recursion traces on Days 3–5.

5. Why O(n log n)

Draw every call as a box in a tree, one row per level (n = 8):

level 0:  [8 items]                          merge work: 8
level 1:  [4]        [4]                     merge work: 4 + 4 = 8
level 2:  [2]  [2]   [2]  [2]                merge work: 8
level 3:  [1][1][1][1][1][1][1][1]           base cases, no merging
  • How many levels? Each level halves the pieces, so it takes log₂ n levels to get down to 1 item (8 → 4 → 2 → 1: 3 levels).
  • Work per level? The pieces on one level hold all n items between them, and merging is linear, so O(n) per level.

Total: log n levels × n work = O(n log n). It doesn't care what the input looks like: sorted, reversed or random, the tree has the same shape. Best, average and worst case are all O(n log n).

nn² (insertion, worst)n log₂ n (merge)
1,0001,000,000≈ 10,000
1,000,0001,000,000,000,000≈ 20,000,000

The price is memory. Every merge builds a new array, so merge sort needs O(n) extra space (plus O(log n) for the call stack). Insertion sort needed O(1). And with slicing, every call also copies its half: still O(n) per level, so the total stays O(n log n).

6. Bonus: counting inversions while you merge

An inversion is a pair i < j with arr[i] > arr[j]: a pair in the wrong order. Yesterday you saw that insertion sort makes exactly one shift per inversion. Counting them with two loops is O(n²). Merge sort can count them in O(n log n):

left = [2, 4]   right = [1, 3]
take 1 from right: 2 and 4 are still waiting in left, and both are > 1  → +2
take 2 from left
take 3 from right: 4 is still waiting in left                        → +1
take 4 from left                                                     → total 3

When you take right[j] before left[i], every value from left[i] to the end of left is bigger (left is sorted), so you count left.length - i inversions in one step. Add the inversions inside left and inside right (found by the recursive calls) and you have them all.

7. Predict the output

Work it out first, then reveal.

merge([1, 5, 6], [2, 3]): how many comparisons does the main loop make?

3: (1, 2) take 1, (5, 2) take 2, (5, 3) take 3. Now b is used up, the loop stops, and 5 and 6 are copied with no comparisons at all. Merging n + m items takes at most n + m − 1 comparisons, often fewer.

How many levels of splitting for 16 items? For 17?

4 and 5. 16 → 8 → 4 → 2 → 1 is 4 halvings. 17 splits into 8 and 9, and the 9 needs one extra level: 9 → 5 → 3 → 2 → 1.

Merge sort on an already sorted array of 1,000 items vs insertion sort on it: which does less work?

Insertion sort! On sorted input it's O(n): about 1,000 comparisons. Merge sort always builds its full tree: about 10,000 operations. Big-O is about the worst case; know your input.

What does mergeSort do without the base case, on [7]?

It splits [7] into [] and [7], and calls itself on [7] again. Forever, until RangeError: Maximum call stack size exceeded. The base case length <= 1 handles both [] and one item.

How many inversions does [4, 3, 2, 1] have?

6: every one of the 4 × 3 / 2 pairs is in the wrong order. Reverse sorted is the maximum, n(n−1)/2.

where this shows up

Interviews: "merge two sorted arrays / lists", "merge k sorted lists", "sorted squares", "intersection of two arrays", "count inversions" and "merge intervals" are all this merge step with two pointers. "Sort a linked list" is merge sort, because linked lists can't jump to the middle cheaply but merge beautifully.

Later topics: divide and conquer comes back in binary search (Days 10–12: keep only one half), in trees (a node, its left subtree, its right subtree) and in many "split the problem in two" problems. Merging k lists efficiently needs a heap, in Phase 3.

8. What's next

Merge sort does its work after the recursive calls (the merge). Tomorrow, quick sort flips that: it does the work before (a partition around a pivot), then sorts the two sides, with no merge at all, in place, and usually even faster in practice.
