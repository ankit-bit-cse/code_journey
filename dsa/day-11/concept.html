Binary search on tricky arrays

Binary search doesn't need a perfectly sorted array. It needs one thing: a look at mid that lets you throw half away for sure. Today: rotated arrays, peaks, matrices and pairs, all in O(log n).

← Day 10Day 12 →

1. The real rule of binary search

Yesterday every search was on a sorted array. But look at what the loop really does each step: it looks at mid, answers one question, and keeps the half where the answer must be. Sorting is just one way to make that question answerable.

So the question to ask on any new problem is: "If I look at mid (and maybe its neighbour), can I tell which half the answer is in?" If yes, it's a binary search, sorted or not.

// versions 1..8:  good good good good good bad bad bad
//                                         ^ first bad
// No array at all. isBad(v) answers "is v bad?", and the answers
// go no, no, ..., yes, yes. The first "yes" is a lower bound (Day 10).

A function can be the "array". When a question hands you isBad(v), call it with mid exactly like you'd read arr[mid]. Each call might be slow (think: building and testing a whole program version), so the number of calls is what you count.

2. Rotated sorted arrays

Take a sorted array and move some items from the end to the front. That's a rotation:

[2, 5, 8, 11, 15, 20, 24]      // sorted
[15, 20, 24, 2, 5, 8, 11]      // rotated 3 times to the right
//            ^ the "drop": the only place where a number is
//              bigger than the next one

It's two sorted runs glued together. Now cut it at any mid. The drop is on one side only, so at least one half is fully sorted. How do you tell which?

if (arr[lo] <= arr[mid]) {
  // no drop between lo and mid: the LEFT half [lo..mid] is sorted
} else {
  // the drop is between lo and mid: the RIGHT half [mid..hi] is sorted
}

And in a sorted half, "is x in here?" is just a check against its two ends: arr[lo] <= x && x < arr[mid].

4. The minimum of a rotated array

The minimum sits right after the drop. Compare arr[mid] with the last item of the range, arr[hi]:

function findMinIndex(arr) {
  let lo = 0, hi = arr.length - 1;
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (arr[mid] > arr[hi]) lo = mid + 1;  // the drop is right of mid
    else hi = mid;                         // mid..hi sorted: min is mid or left
  }
  return lo;
}
findMinIndex([15, 20, 24, 2, 5, 8, 11]);   // 3

The minimum started at index 0 and moved one place right per rotation, so its index is how many times the array was rotated.

Why arr[hi] and not arr[lo]? If the array is not rotated at all, arr[mid] > arr[lo] is true everywhere, and comparing with arr[lo] would walk you right, away from the minimum at index 0. Comparing with arr[hi] handles both cases.

5. Watch it run: peak finding walks uphill

A peak is an item bigger than both neighbours (outside the array counts as -Infinity). Compare arr[mid] with arr[mid + 1]: if the next one is higher, you're on an uphill slope, and the slope has to stop somewhere to the right, so a peak is there. This array has three peaks; watch which one the search finds.

It found the peak 6, not the biggest value 12. Binary search finds a peak, not the highest one. Finding the maximum needs a look at every item: O(n).

7. When you don't know the size

Sometimes there is no length: a huge sorted stream, or a get(i) that returns Infinity past the end. Binary search needs a hi, so find one by doubling:

let hi = 1;
while (get(hi) < x) hi = hi * 2;     // 1, 2, 4, 8, 16, ...
let lo = Math.floor(hi / 2);
// now x (if it's there) is inside [lo, hi]: binary search as usual

If x is at index n, the doubling takes about log₂ n steps and the search another log₂ n, so it's still O(log n). This trick is called exponential search.

8. Pairs in a sorted array

In [1, 1, 3, 3, 4, 7, 7] every number is a pair except 4. Before the single one, pairs start at even indices (0, 2). After it, they start at odd indices (5). So looking at an even mid and its right neighbour tells you which side the single one is on. A pattern in the positions, not the values, is enough for binary search.

9. Predict the output

Say the answer out loud first, then reveal.

[6, 7, 1, 2, 3, 4, 5], lo = 0, hi = 6: which half is sorted?

mid = 3, arr[0] = 6 and arr[3] = 2. 6 > 2, so the drop is in the left half, and the right half [2, 3, 4, 5] is sorted.

How many times was [6, 7, 1, 2, 3, 4, 5] rotated?

2. The minimum 1 is at index 2. (Moving the last item to the front twice: [1..7] → [7, 1, ..., 6] → [6, 7, 1, ..., 5].)

Peak search on [3, 4, 5, 6]: what index?

3. It's uphill all the way, so the last item is a peak (its right neighbour counts as -Infinity).

In a 4 × 5 matrix, where is flat index 13?

Row Math.floor(13 / 5) = 2, column 13 % 5 = 3. Note: divide by the number of columns, not rows.

The plain binary search from Day 10, looking for 5 in [4, 5, 1, 2, 3]

-1, even though 5 is at index 1! mid = 2 holds 1 < 5, so it throws away the left half (and the 5 with it), then checks 2 and 3 and gives up. Rotated arrays need the "which half is sorted" check.
