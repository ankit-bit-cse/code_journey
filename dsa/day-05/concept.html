Recursion trees and memoization

When a function calls itself twice, the calls grow into a tree, and the tree can explode. Today you watch it explode, then tame it with one small object that remembers answers.

← Day 4Day 6 →

1. Two calls per step make a tree

The Fibonacci numbers start 0, 1 and then each one is the sum of the two before it: 0, 1, 1, 2, 3, 5, 8, 13, … The definition turns straight into code:

function fib(n) {
  if (n < 2) return n;               // base cases: fib(0) = 0, fib(1) = 1
  return fib(n - 1) + fib(n - 2);    // TWO recursive calls
}

Yesterday most functions made one call each, so the calls formed a chain. Here every call (except the base cases) makes two, so they form a tree:

                 fib(4)
             /          \
        fib(3)           fib(2)
        /    \           /    \
    fib(2)  fib(1)   fib(1)  fib(0)
    /    \
 fib(1) fib(0)

The stack only ever holds one path from the top to a leaf, so the space is O(n). The time is the number of boxes in the tree, and that is the problem.

2. Watch it run: the call tree of fib(4)

Each column is one call, in the order the calls happen; each row is a depth (row 0 is the first call). The coloured box is the call running now, yellow ones are waiting for their children, green ones have returned, and red ones are repeats: a question that was already answered earlier.

9 calls to get the answer 3, and fib(2) was worked out twice from scratch. In bigger trees it gets much worse.

4. Memoization: remember every answer

Keep a memo: a place to write down each answer the first time you compute it. Before doing any work, look in the memo. JS for DSA Day 8's Map is perfect for it (a plain object works too):

function fib(n, memo = new Map()) {
  if (memo.has(n)) return memo.get(n);   // 1. asked before? answer at once
  if (n < 2) return n;                   // 2. base cases
  const ans = fib(n - 1, memo) + fib(n - 2, memo);
  memo.set(n, ans);                      // 3. write it down
  return ans;
}

Now fib(k) is computed once for each k. Every other time it is asked, it returns straight from the memo: a call with no children. About 2n calls in total: O(n) time.

Pass the same memo down. The default memo = new Map() runs only when the argument is missing, so the very first call makes the memo and every recursive call receives that same one. Forget to pass it (fib(n - 1)) and each call makes a brand-new empty memo: you are back to exponential.

5. Watch it run: the memo fills up and cuts the tree

The boxes are the memo: box k holds fib(k) once it is known. The first trip goes straight down the left side; on the way back up each answer is written down. After that, every second call is a memo hit and returns at once.

11 calls for fib(6) instead of 25. For fib(40): 79 calls instead of 331 million.

6. Predict the output

Say the answer out loud first, then reveal.

How many calls does plain fib(3) make?

5: fib(3), fib(2), fib(1), fib(0), and fib(1) again. calls(3) = 1 + calls(2) + calls(1) = 1 + 3 + 1.

const memo = { 0: 0 }; if (memo[0]) "hit"; else "miss";

"miss"! The stored answer is 0, and 0 is falsy. Test with 0 in memo or memo.has(0), which ask "is the key there?", not "is the value truthy?".

const m = {}; m[[2, 3]] = 7; Object.keys(m)

["2,3"]. Object keys are strings, and an array turns into "2,3". That is why for two parameters we build the key ourselves: `${r},${c}`.

Memoized fib(5), then (with the same memo) fib(5) again. How many calls the second time?

1. The answer is already in the memo, so the first line returns it.

How many moves for the Tower of Hanoi with 4 disks?

15. moves(n) = 2 × moves(n - 1) + 1, so 1, 3, 7, 15: it is 2ⁿ - 1.

7. Counting ways: split on the last move

"How many ways…" questions have a recursive answer when you ask how the last move could have happened. Say a frog crosses n stones, jumping 1 or 3 stones at a time. To land on stone n, its last jump came from stone n - 1 or from stone n - 3, and those are different ways:

ways(n) = ways(n - 1) + ways(n - 3)
ways(0) = 1      // already there: one way (do nothing)
ways(negative) = 0

That is a recursion tree just like fib's, full of repeated questions, so it needs a memo too. Grids work the same with two numbers: the first move is either down or right, and each leaves a smaller grid. Their memo key is `${r},${c}`.

When does a memo help? Only when the same call (same arguments) happens more than once. In take/skip with a running sum, or in the Tower of Hanoi, nearly every call is different, so a memo just wastes memory.

8. Tower of Hanoi: trust the recursion

Disks sit on peg A, biggest at the bottom. Move them all to another peg, one disk at a time, never putting a bigger disk on a smaller one. Don't plan every move. Think about the biggest disk only:

  1. it can only move when every other disk is out of the way, on the spare peg;
  2. so: move the n - 1 smaller disks to the spare peg (a smaller Hanoi!), move the big one, then move the n - 1 back on top of it (another smaller Hanoi).

Here are 3 disks going from A to B, using C as the spare. In the grid, column 0 is peg A, column 1 is peg B and column 2 is peg C; the bottom row is the bottom of each peg, and the number is the disk size.

moves(n) = moves(n - 1) + 1 + moves(n - 1) = 2ⁿ - 1. With 64 disks, at one move a second, that is about 585 billion years.

memoization is the door to dynamic programming

"Recursion + a memo" is called top-down dynamic programming, and it is one of the most asked interview topics: Climbing Stairs, House Robber, Unique Paths, Coin Change, Decode Ways all start from a recursion that splits on a choice, then add a memo. Phase 5 is all about it. Recursion trees also explain the cost of backtracking (Phase 4) and of merge sort (Day 8), whose tree has only log n levels.
